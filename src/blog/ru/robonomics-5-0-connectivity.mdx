Первая часть была про протокол: рантайм, репозитории, архитектуру 5.0. Эта — про дорогу, по которой туда приходят данные: от датчика у кого-то на балконе до записи в цепочке, которую может проверить любой.

Это самый незаметный слой системы, и именно он решает, чего стоит всё остальное. Цепочка, которая честно хранит то, что ей передал посредник, доказывает только одно: посредник так сказал.

## Как данные идут сейчас

Карта sensors.social сейчас работает на `sensors-connectivity` — сервисе на Python, который делает эту работу уже несколько лет. Altruist отправляет по HTTP измерение в JSON, подписанное своим ключом Ed25519. Сервис проверяет подпись и подписку устройства, публикует показание в IPFS pubsub для живой карты, собирает показания в пачки, закрепляет каждую пачку в IPFS и записывает её хеш в парачейн как datalog.

Это работает, и сервис по-прежнему развивается: на прошлой неделе вышла версия 1.7.2 с поддержкой датчика радиации. Но посмотрите, что оказывается в цепочке: ссылка на файл, записанная аккаунтом сервиса. Цепочка может подтвердить, что сервис опубликовал этот хеш, и ничего — о показаниях внутри файла. Чтобы доверять данным, нужно доверять тому, кто держит сервис, и шлюзам, которые хранят файл.

5.0 меняет единицу доверия. По сети идёт и в цепочку попадает то, что подписал сам датчик.

## Подписанный конверт

Новый формат живёт в отдельном репозитории [`connectivity-protocol`](https://github.com/airalab/connectivity-protocol). Он начат в августе, опубликован на [buf.build](https://buf.build/airalab/connectivity-protocol) под лицензией Apache-2.0. Одну схему используют прошивка Altruist, сервисы связи и интерфейс sensors.social.

Внешний слой — четыре поля:

<RbCode>

```protobuf
message SignedEnvelope {
  bytes sensor_id = 1;  // открытый ключ Ed25519 датчика, 32 байта
  bytes nonce     = 2;  // случайное значение, своё для каждого сообщения
  bytes message   = 3;  // телеметрия, сырые байты protobuf
  bytes signature = 4;  // Ed25519 от sensor_id + nonce + message, 64 байта
}
```

</RbCode>

Главное правило — про байты. Сериализация protobuf не детерминирована: раскодируйте сообщение и закодируйте снова — байты могут получиться другими при том же смысле. Другие байты ломают подпись. Поэтому устройство сериализует один раз и подписывает; каждый следующий слой проверяет и пересылает конверт нетронутым; бэкенд может раскодировать его для индекса, но хранит исходные байты. Никто не перекодирует. Так показание проходит через три сервиса и радиосеть и всё ещё сверяется с ключом устройства, которое его сняло.

Внутри конверта сообщение несёт короткий заголовок и измерения:

<RbCode>

```protobuf
message Meta {
  uint64 node_id   = 1;  // узел устройства в дереве CPS Робономики
  uint64 timestamp = 2;  // UTC, миллисекунды
}
```

</RbCode>

`node_id` — то место, где этот слой встречается с первой частью. Датчик больше не определяется полем владельца, вшитым в прошивку: он узел в дереве CPS, той же топологии, вокруг которой построен рантайм 5.0. Измерения типизированы по плате — Urban для уличных, Insight для комнатных, — и каждое можно отправить открыто или шифротекстом для конкретного адресата: например, городу точные координаты, а публичной карте приблизительные. Шифротекст протокол несёт как непрозрачные байты и сознательно не фиксирует шифр.

## Пакет LoRa перекроил формат

Сначала конверт проектировали под HTTP, где лишние байты ничего не стоят. Потом попробовали отправить его через сеть LoRa.

Altruist часто стоит там, где нет Wi-Fi: на крышах, в парках, на стройках. Meshtastic — открытая прошивка, которая превращает дешёвые платы LoRa в самоорганизующуюся радиосеть, и для таких мест она напрашивалась. Ограничение у неё жёсткое: пакет LoRa — 255 байт, и всё. Спецификация транспорта, которую мы написали в сентябре, считает так:

<RbCode>

```text
255  пакет LoRa
-16  заголовок Meshtastic
-12  шифрование PKI (тег + доп. nonce)
 -6  поля Data в Meshtastic (порт + длина)
 -2  запас, измеренный на реальной прошивке
---
219  байт на наш кадр; 1 из них — тип кадра
```

</RbCode>

Теперь вычтите сам конверт. 32 байта ключа, 64 байта подписи, 16 байт nonce и их теги — около 120 байт. На время, номер узла и все измерения остаётся меньше сотни байт, если показание должно влезть в один пакет и не дробиться в радиоканале, где может потеряться любой фрагмент.

Первая схема не влезала. Каждое измерение было `double`: восемь байт плюс тег — для датчика температуры с реальным разрешением в сотую градуса. Поэтому в сентябре схему переделали под радио:

<TextCard alignContent="left" back="white" shadow="gray">

**Масштабированные целые вместо double.** Температура в 0,01 °C как `sint32`, влажность в 0,01 %RH, давление в 0,1 Па, PM2.5 и PM10 в 0,1 мкг/м³, CO₂ и шум в целых единицах. Varint в protobuf делает маленькие числа маленькими и на проводе.

**Одна метка времени на сообщение** — в `Meta`, а не у каждого измерения.

**`node_id` из CPS вместо адреса владельца** — число в несколько байт вместо 32-байтного ключа.

</TextCard>

Для HTTP ничего из этого не было нужно. И всё это удешевляет путь по HTTP тоже.

Сам транспорт Meshtastic описан нарочито скучно: шифрованная адресная отправка на известный шлюз с подтверждением; лучше не отправить, чем молча откатиться на более слабое шифрование канала; дробить пакет только когда он действительно не влезает; повторы оставить прошивке Meshtastic, а не запускать поверх неё второй цикл повторов. Стенд — Altruist Urban, который по UART говорит с платой Heltec V4 на 868 МГц, и Raspberry Pi 4 с LoRa-модулем в роли шлюза; схема и настройка — в [репозитории hardware](https://github.com/airalab/hardware).

## Облачный конвейер

На приёмной стороне [`connectivity-cloud`](https://github.com/airalab/connectivity-cloud) заменяет один процесс на Python набором небольших сервисов на TypeScript вокруг журнала Kafka:

<RbCode>

```text
датчик -> POST /v1/telemetry (endpoint)
            подпись, окно времени, nonce, допуск
            202 только после подтверждения Kafka
              |
              +-> pubsub-broadcaster  -> libp2p GossipSub -> живая карта
              +-> heartbeat-tracker   -> какие датчики на связи
              +-> batcher             -> пачки, zstd, <= 8 КБ
                    +-> blockchain-anchor -> cps.setPayload
```

</RbCode>

Endpoint отклоняет сообщение, если время в нём расходится больше чем на пять минут, если nonce уже встречался или подпись не сходится, и отвечает датчику, только когда событие надёжно легло в Kafka. Всё дальнейшее читает журнал независимо, так что медленная цепочка не тормозит живую карту.

Результат определили два решения этой осени.

**В цепочку идут сами данные, а не ссылка на них.** До сентября конвейер повторял старую схему: пачка, закрепление в IPFS, CID в цепочку. В конце сентября шаг с IPFS убрали. Теперь batcher сжимает каждую пачку подписанных конвертов в zstd и режет её под 8 КБ, а сервис якорения записывает эти байты в паллет CPS через `cps.setPayload`. В цепочке лежат сами показания, по-прежнему в подписях датчиков, и никому не нужно держать файл закреплённым, чтобы запись оставалась читаемой.

**Кому можно отправлять, решает дерево CPS.** В конце октября статический список разрешённых датчиков уступил место проверке по цепочке: датчик принимается, если его узел CPS лежит под корневым узлом sensors.social. Добавить датчик в сеть — значит выполнить операцию в цепочке, в том же дереве, которым 5.0 описывает все остальные устройства; сервису связи остаётся только его прочитать.

В начале ноября сервисы подготовили к Google Cloud Run: TLS с аутентификацией до Redis и Kafka, атомарное хранилище nonce, общее для всех экземпляров, и отказ запускаться в рабочем режиме, если что-то из этого выключено.

## Без облака: edge-шлюз

Не каждой установке нужны Kafka и облачный аккаунт. Для одноплатного компьютера на крыше в репозитории [robins](https://github.com/airalab/robins) есть `edge`: один бинарник, который принимает те же подписанные конверты по HTTP, делает те же проверки — подпись, допуск по CPS, защиту от повторов — и публикует принятое в ту же тему GossipSub, со встроенными health-проверками и метриками Prometheus. В нём есть и приём из Meshtastic, так что шлюз на конце радиоканала и шлюз в сеть могут быть одним маленьким устройством. Тот же бинарник служит набором инструментов: создать ключ датчика, собрать сообщение из командной строки, подписать, посмотреть, что внутри.
